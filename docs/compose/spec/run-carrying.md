# 案C run の成果が次へ残るものにする

## Report

## [S1] Problem

### S1.1 run が終わっても何も残らない

`feature/run-end` でゲームはようやく終わるようになった。`RunSummary`（`run_summary.py`）が到達深度・撃破数・喰いスキル数・経過ターン・死因・経過時間を保持し、画面に提示する。

しかしその summary の消費者は `engine/engine.py` の表示処理とテストだけである。セーブされず、`game_state_data` にも残らず、次回の run に渡る経路が存在しない。**終わらせるという地点を作っただけで、その先の受け皿を作っていない。**

### S1.2 2回目の run は 1回目と何も変わらない

リセットは転生のみ（`engine/engine.py` の reincarnation）で、ゲートはレベル 50〜200。リセット時に得られるのは `level` と `exp` の初期化、ランダムな欠片 1 つ、そして 2 つの cycle modifier だが、**その modifier の効果はどのゲームシステムからも読まれていない**。

永続報酬トークンは `data/meta_progression.yaml` の `damage_boost_1` / `gold_gain_5` 等だが、これらを参照する Python は**テスト以外で 0 件**。`data/meta_goals.yaml` の `permanent_bonus`（`magic_power` / `resistance_all` / `potential_bonus` / `karma_gain_multiplier`）も同様で、0 件の読み手。

この状態を前提に、案A で「Lv1 スライム1戦あたりの被ダメージ 0.13」という測定が出た。**プレイヤーは死なない。** 測定器は正しく「偏差している」と報告したが、正しくもない数字を正しく統計しただけで、ゲームの側は何も変わっていない。

### S1.3 実装済みの構造が受け皿を欠いている

- `meta_progression_system.py`（20,306 バイト）と `meta_progression_data/generated/` に目標・報酬の枠組みがある
- `skill_eater_bank_dungeon.py` に「スキルバンク」がある。`active_debuffs` は表示文字列で、**本番呼び出し元はテストのみ**
- `data/achievements.yaml`（12 件）と `data/titles.yaml`（12 件）が定義済みで、獲得判定に run の集計が渡せる形になっている
- `save_system.py` は Engine 全体を pickle する。run 終了時の永続データを置く場所は既に技術的に存在しないわけではない

## [S2] Design

### S2.1 run の結果を永続し、次回に引き継ぐ

- 死亡時に `RunSummary` から**永続不可能な値だけ**を抜き出し、ディスクに書き出す。候補は到達深度・撃破数・経過ターン・死因・喰いスキル id 一覧。
- 保存先は既存のセーブ規約に従い、新しいフォーマットを捏造しない。`savegame.bin`（Engine の pickle）と混ぜず、run 履歴として別ファイルにする。`savegame.bin*` は追跡ファイルであり、テストが汚さないこと。
- 起動時にこれを読み、次の run の提示に使う。具体的には「前回の到達深度」「自己最高記録」を表示する。** この 2 つはプレイヤーが run をまたいで実際に比較する値である。**
- 読み込みに失敗した場合（ファイルが無い・壊れている）は、**黙って無視しない**。初回起動である旨と、履歴が読めなかった理由を示す。

契約: run を終えると記録ファイルが生成され、次回起動時に読み込まれる / 2回目の起動で前回深度と最高記録が提示される / 履歴ファイルが壊れていても起動は成功し理由が明示される。

### S2.2 永続報酬トークンを実装か、記録から外す

`data/meta_progression.yaml` の `damage_boost_1` / `gold_gain_5` 等と `data/meta_goals.yaml` の `permanent_bonus` は、**実装されるか、到達不能である旨が明記されるかの二択**にする。今の「定義だけある」状態を放置しない。

- 実装する場合、どのシステムに効くかを明示し（例: ダメージ加算は `CombatSystem` 側）、読み手を 1 箇所に集約する。**効果を足すだけの無検証実装はしない** — テストが通ることとゲームに効くことは別である。
- 実装しない場合、該当トークンを読まれない状態に整理し、「未実装のため保留」とデータファイルに記す。

**偽りの禁止**: どちらを選ぶ場合でも、「獲得できる」「強化される」の語を、 Positioning 読めないトークンには使わない。`[S2.1]` で保存した履歴についても同様。

契約: `meta_progression.yaml` の各トークンが「実装済みで実読される」か「保留と明記されている」かのどちらかであって、現状のように無言で放置されていない。

### S2.3 「Lv1 スライムに 0.13 ダメージしか受けない」を 1 つの指標として扱う

案A で得た測定値を、**ゲームの側**から動かす。計測器だけを直しても結果は変わらない。

- `CombatSystem` のLv1 スライム基準値と `data/balance_standards.yaml` の `standards.levels` の乖離を解消する。ただし**根拠なく数値を恣意的に触らない**。最初のステップとして、Lv1 スライム 1 戦が妥当なターン数で決着し、双方の体力が消耗する値になるまで調整する。
- 目標値を先に決める: 「Lv1 のスライムに 10 ターン以内に倒され、Lv1 プレイヤーは数ターンのやり合いで 20〜40% の体力を失う」程度。これは「毎戦全快」を排除するための閾値であり、難易度曲线全体の設計ではない。

契約: `pytest tests/test_balance_report_honesty.py` の基準違反のうち、Lv1 の HP と攻撃の超過が解消され、`gold_per_dungeon_floor` 以外の自動判定が FAIL を返さなくなる / 変更後の `balance_report.json` に測定方法(method)が記録されている。

## [S3] Out of Scope

- 難易度曲線全体の設計。S2.3 は Lv1 の基礎値 1 点と、Lv1 スライム 1 戦だけを対象にする。
- 転生（reincarnation）の再設計。`cycle_modifiers` が未読である件は記録するが，本次は実装しない。
- 、獲得ゴールドの実害（`managers/combat_manager.py:56` が完了分岐の外側で毎キルの全クエスト報酬を支払うこと）は原因が判明している別の feature とする。ただし S2.3 の判定結果として判明している間は FAIL のままにする。
- リーダボード、通信、cloud save。
- 進捗バーの UI 設計。S2.1 の提示は既存のログ流儀に揃える。
